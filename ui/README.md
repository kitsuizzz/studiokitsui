# ui — the shell page (Studio + Chat)

`ui/index.html` is the one page nnstudio serves at `/` and `/studio`: the top
bar, the session sidebar, the canvas main, and the `#nn-chat` mount for the
vendored Chat SPA. It is **generated**; edit the sources in `ui/src/`.

```
ui/src/index.html        markup, title, favicon, brand logo
ui/src/css/*.css         tokens -> base -> Salon skin -> brand block
ui/src/js/*.js           numbered slices, concatenated in numeric order
tools/build_ui.py        assembles ui/index.html; `--check` fails when stale
```

Build it after any source change:

    .venv/bin/python tools/build_ui.py          # write ui/index.html
    .venv/bin/python tools/build_ui.py --check  # what tests/run.sh runs

The page stays self-contained at runtime: the server only serves
`ui/index.html`, and `tests/run.sh`, `tests/ui_boot.js`, `tests/brand_test.py`
and the two crypto/seam tests all read that one file. The split is a source
layout, not a runtime module system.

## The cascade (CSS)

| file | what it owns |
|---|---|
| `css/00-tokens.css` | the Salon palette (light/dark), legacy aliases, the three typefaces |
| `css/10-base.css` | the page base and the pre-Salon component rules |
| `css/20-salon.css` | the Salon skin over the canvas. **This file wins.** |
| `css/30-brand.css` | generated by `brand/tools/make_brand.py` — do not edit |

If a canvas rule looks ignored, check `20-salon.css` first: it overrides the
finish of most rules in `10-base.css`. When you add a new canvas rule, put it
in `20-salon.css` with the other Salon rules. Tokens go in `00-tokens.css`,
never as a literal colour in a component file.

## The script (JS)

top-level declarations, so the result is still one classic `<script>` — no
modules, no wrapper, no build-time imports. The numeric prefix is the order,
not a filename convention to improvise with.

### The one ordering rule

Function declarations hoist, so a function may call one from a later slice.
**Top-level `let`/`const`/`try`/`for` statements do not.** They run where they
sit, in numeric order. That is why the slices keep the original top-level
order; do not move state from a later slice into an earlier one without
checking every initializer. If in doubt, keep the declaration where it is.

## Hot paths

A full `bxRender()` rebuilds the grid, every card, every wire, and every
embedded pane. It is the right cost for a structural change, never for a
pointer move:

- **Dragging a box** uses `bxDragPaint()`: it moves the existing card `<g>` with
  a `transform` and re-routes only the wires touching the moved boxes.
- **Shift+drag marquee** uses `bxMarqueePaint()`: one rect, updated in place.
- **Corner-resizing** uses `bxResizePaint()`: one card is rebuilt, and its live
  pane is carried over so a dataset table or agent log keeps its scroll.
- **The drop** calls `bxRender()` once, to put the cards back on their real
  coordinates and refresh their state.
- **Panning** only updates the viewBox and the grid.
- **The VRAM estimate** is computed when its menu opens (and while it is open),
  not on every canvas render.
- **Task log polls** repaint only the live agent/training panes, and an idle
  poll with no new tokens does no DOM work; the 2 s list poll refreshes the
  rest.
- **Pane scroll restore** reads layout only when the canvas actually has panes.
- **Host resizes** (the first layout, a sidebar fold) re-render once through a
  debounced `ResizeObserver`, so the SVG viewBox keeps the canvas's real aspect
  instead of cropping the design with the boot fallback.

Keep new pointer-move code on the incremental path; add a full render only at
the end of the gesture.

## State ownership

| state | owner |
|---|---|
| `BX` | the open canvas document, view, stack, selection, drag/wire state |
| `BXSESSION`, `BXTAB`, `bxTabSeq` | the open canvases and the active tab |
| `BXACCT`, `BX_TS`, `BX_KEY_PREFIX` | the account, its key, the bot-check widget |
| `BX_E2E`, `BX_CANVAS_MAX` | the sealed-store format (pinned by `tests/studio_crypto_test.js`) |
| `BXCHAT`, `BXVIEW` | the chat projection and which main is showing |
| `BX_BACKEND`, `BXRUN` | the backend choice and the last run |
| `BXTASKS` | the task list cache |
| `BX_TEMPLATES`, `BX_PALETTE` | the template builders and the palette catalogue |

The shell and the Chat SPA share one account, one session list and one theme;
the bridge is in `95-shell-chat.js` on this side and `src/lib/canvasLink.ts` on
the other. A session is a conversation plus its canvas; the canvas half owns
the design, the chat half owns the conversation.

## Where do I change …?

- **A token / theme colour** — `css/00-tokens.css` (both themes; the Chat half
  has its own copy in `chat/frontend/src/styles/tokens.css`).
- **The look of a canvas control** — `css/20-salon.css`; if it is a new rule
  for a legacy element, add it there rather than editing `10-base.css`.
- **A box kind** — `10-values.js` (`BX_KINDS`, labels, shape), `20-model-link.js`
  (ports), `40-model-edit.js` (`bxConfigure`), `75-card-render.js` (`bxCard`),
  `135-models-weights.js` (`bxForm`), then the engine.
- **A new box action / menu item** — `80-menus-toolbar.js`.
- **Persistence or the sealed store** — `85-account.js`; the Chat half's reader
  is `src/lib/canvasLink.ts`. Keep the AAD (`canvas|<id>`, `session|current`) and
  the HKDF salt/info unchanged unless both sides change together.
- **A session/tab rule** — `90-tabs-session.js`; the list rendering is in
  `95-shell-chat.js` (`bxTabsRender`).
- **The Chat \| Studio crossing** — `95-shell-chat.js` (`bxViewSet`,
  `bxStudioOpen`, `bxCanvasBindSession`) and `src/App.tsx` for the SPA side.
- **A toolbar dropdown** — `80-menus-toolbar.js` (markup and toggles) plus
  `105-run-backend.js` for Backend/Run content.

## Tests and seams

Run the fast set after a source change:

    .venv/bin/python tools/build_ui.py
    node tests/ui_boot.js
    node tests/studio_crypto_test.js
    node tests/canvas_link_test.js
    .venv/bin/python tests/brand_test.py
    ./tests/run.sh

`tests/ui_boot.js` evals the generated `<script>` and exports a long list of
`bx*` helpers as its test seam. `tests/studio_crypto_test.js` and
`tests/canvas_link_test.js` slice the generated file between literal markers
(`const BX_E2E = {`, `const BX_CANVAS_MAX`, `function bxCryptoReady()`,
`// the shared key cache`, `function bxCanvasAad(id) {`,
`async function bxCanvases()`). If you move one of those markers, update the
tests in the same change — otherwise the failure is a terse "the UI script
moved". Keep the account crypto and its markers together in `65-clipboard-json.js`
and `85-account.js`.

`brand/tools/make_brand.py` writes the marked `brand:logo` / `brand:favicon`
regions in `ui/src/index.html` and the `brand:css` region in
`ui/src/css/30-brand.css`, then rebuilds `ui/index.html`. `tests/brand_test.py`
pins the generated page.

## History

This used to be a single 13,790-line page. The split is deliberately
mechanical: the concatenation of `ui/src/js/*.js` is the old script and the
concatenation of `ui/src/css/*.css` is the old stylesheet, in the same order.
That is the guarantee to preserve when moving code: behaviour first, tidier
files second.
